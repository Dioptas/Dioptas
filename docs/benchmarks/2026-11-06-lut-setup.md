# Shared versus separate lookup-table setup, 2026-11-06

Sharing considerably reduces setup time and peak memory, even when the separate tables are prepared concurrently. Medians of five trials per case:

| Frame workers | Separate setup, s | Shared setup, s | Wall-clock speedup | CPU seconds: separate / shared |
| --- | --- | --- | --- | --- |
| 4 | 1.495 | 0.683 | 2.19x | 6.05 / 1.49 |
| 8 | 2.494 | 0.621 | 4.02x | 16.83 / 1.87 |

| Frame workers | Separate peak RSS, GiB | Shared peak RSS, GiB | RSS when ready: separate / shared, GiB |
| --- | --- | --- | --- |
| 4 | 7.12 | 2.42 | 6.54 / 2.42 |
| 8 | 12.31 | 2.66 | 10.45 / 2.66 |

Each trial ran in its own fresh Python process. Neither variant inherited an already prepared table, warmed native allocator or another variant's resident plans. Shared setup creates one immutable plan and N single-thread compute handles; separate setup creates exactly N independent immutable plans concurrently and one single-thread handle for each. Both variants use the same native binary and API. Geometry construction uses a global Rayon pool of N threads in either variant, preventing an N-by-N build-thread advantage. No unused common parent plan is prepared for the separate control.

The timer starts before creating unprepared integrators. It includes geometry and correction arrays, float64 CSR/CSC tables, application executor startup as used, and native worker-handle/thread-pool creation. It stops when all N handles have returned ready. It excludes process startup, Python/library imports, HDF5 reading, mask generation, integration/validation and pool teardown. `prepare_dynamic1d` eagerly completes geometry/CSR/CSC preparation before returning. This is an isolated native-plan setup measurement, not total Dioptas application startup or first-image latency.

Inputs and settings match the preceding Eiger comparisons: original `eiger_0000.h5`, shape 3262×3108, 2000 two-theta bins, pixel splitting, float64 weights/corrections/accumulators, polarization 0.965 and solid-angle correction. The first original Eiger frame and its original static mask plus threshold >230 mask validate every handle **after** the timer and memory capture. Pixel values and dynamic masks do not enter the geometry-table build itself. No pixel precision was reduced. Every worker matched an independently configured fixed-mask CSR reference; maximum relative L2 error was 3.71e-16. Median first integration checks were about 19–32 ms per worker, outside the setup timer.

Five alternating paired trials were run for 4 and 8 workers, reversing both worker-count order and variant order between rounds. No samples were removed. Four-worker separate/shared ranges were 1.410–1.521 / 0.679–0.707 s; eight-worker ranges were 1.915–3.474 / 0.601–0.626 s. Background activity remained: median other busy cores were 2.06/2.01 for four-worker separate/shared and 2.97/2.28 for eight-worker separate/shared. The eight-plan build therefore has wider timing variation. CPU work also decreases substantially, supporting that the savings come from eliminating duplicated construction, rather than only a favorable scheduling interval.

Peak RSS uses the isolated child process high-water mark, sampled before validation, plus a 10 ms RSS monitor. Initial process RSS was about 0.12 GiB. Memory includes the input frame/mask, process baseline, builder temporary allocations, native tables, allocator retention and worker handles; it is not just the final table byte count. Unlike the prior warm-throughput comparison, each process contains only the measured variant.

This confirms that setup and memory are the substantial benefits of sharing. It does not change the earlier conclusion that warmed-up per-frame throughput is approximately the same with shared and separate plans.

The native library is the same local, unreleased shared-plan build used for previous comparisons (metadata still 0.8.0). No processing implementation was changed for this task; only the setup benchmark and results were added. Script, calibration, mask and native binary hashes are retained with the measurements.

Reproduce with `OMP_NUM_THREADS=1 OPENBLAS_NUM_THREADS=1 RAYON_NUM_THREADS=4 QT_QPA_PLATFORM=offscreen .venv/bin/python -m scripts.benchmark_lut_setup --hdf5 /Users/clemens/Programming/Dioptrin/test_data/eiger_0000.h5 --poni /Users/clemens/Programming/Dioptrin/docs/benchmarks/2026-11-05-bslz4/calibration.poni --mask /Users/clemens/Programming/Dioptrin/test_data/eiger_0000.mask --output docs/benchmarks/2026-11-06-lut-setup.json --repeats 5`. The parent sets each child process's Rayon build budget to its requested worker count.
